Diagrama 01 · camadas

Do silício ao token.

O aios é escrito em cima de uma base de sistema operacional e entrega, no topo, apps e agentes que falam com o mesmo runtime local.

Camadas do sistema

top-down

Cada camada só depende da de baixo: o app conversa com o runtime, o runtime com o núcleo, o núcleo com o modelo em disco — e o modelo nunca sai do dispositivo.

Diagrama 02 · componentes

As peças do runtime.

Interfaces em cima, serviço no meio, núcleo e dados embaixo. O daemon é o único processo que expõe rede, e ele só escuta o loopback.

Diagrama 03 · fluxo

O caminho de uma requisição.

Do prompt que o app envia ao token que sai do modelo, sem sair do processo e sem sair da máquina.

Fluxo de inferência

sequência

O roteamento do Laya é opcional: se a pergunta tipada não trouxer resposta, a requisição segue intacta para o modelo — o fluxo nunca para.

Diagrama 04 · integração

Onde os apps entram.

Cada app próprio conversa com uma parte diferente do runtime — e nenhum dos dois depende de serviço externo.

Integração dos apps com o daemon

ponto a ponto

O Laya entra pela frente, como proxy do endpoint de inferência. O Web SQLite Admin entra pelo lado dos dados, abrindo os bancos locais direto pelo rusqlite.

Laya Gateway

Proxy local entre o agente e o modelo: pergunta tipada à especialista, repassa o resto da requisição sem alterar o formato.

fala com o daemon em POST /api/infer formato de entrada compatível com OpenAI ponto local padrão 127.0.0.1:8790 comportamento fail-open

Web SQLite Admin

Administração de dados com API própria em Rust/Actix: o app é dono do seu banco e conversa direto com o arquivo, sem passar pelo daemon.

acesso a dados por rusqlite superfície web Next.js distribuição sidecar em imagem única mesmo host, processo separado

Runtime edge-ai

Um processo, loopback apenas. Os apps entram por contratos diferentes e nenhum deles altera o caminho do outro.

API JSON painel métricas CPU pura
superfície do sistema contrato entre app e runtime
